## GitHubは「インターネットに公開する」ということ

Publicリポジトリに上げたものは、**世界中の誰でも見られます。**

そしてもう1つ、大事な事実があります。

> **一度pushしたものは、後から消しても「無かったこと」にはできません。**

Gitは**履歴を記録する道具**です。ファイルを消すコミットをしても、
「昔そこにあった」という履歴は残り続けます。

さらに悪いことに、**GitHubに上がった秘密情報は、数分以内にbotに収集されます。**
「APIキーを探すbot」が24時間GitHubを巡回していて、
新しくpushされたキーを自動で見つけて悪用します。**これは誇張ではなく、日常的に起きています。**

---

## 上げてはいけないもの

| 種類 | 具体例 | 何が起きるか |
|---|---|---|
| **APIキー** | OpenAI / Anthropic / AWS のキー | **他人にAPIを使われ、請求はあなたに来ます** |
| **パスワード** | DBのパスワード、管理画面のパスワード | 不正アクセスされます |
| **`.env` ファイル** | 上記がまとめて入っているファイル | 全部漏れます |
| **秘密鍵** | `.pem` `.key` `id_rsa` | サーバーに侵入されます |
| **個人情報** | 顧客リスト、名簿、成績データ | 法的な問題になります |
| **巨大ファイル** | 数百MBのデータセット、`node_modules` | リポジトリが重くなり、みんなが困ります |

### 実際に起きていること

- 学生がOpenAIのAPIキーを含む学習用リポジトリを公開 → 数時間で数十万円の請求
- AWSのアクセスキーを誤commit → 仮想通貨マイニングに悪用され、数百万円の請求

**「自分のリポジトリなんて誰も見ていない」は通用しません。** botは全部見ています。

## `.gitignore` — Gitに「これは無視して」と伝える

> **`.gitignore`**（ギットイグノア）＝ Gitに「このファイルは記録しなくていい」と教えるファイル。

### 仕組み

リポジトリの一番上に `.gitignore` というファイルを置き、そこに書いたファイルは
**`git add` しても記録されなくなります。** `git status` にも出てきません。

**このリポジトリにも既に置いてあります** → [`.gitignore`](../.gitignore)

### 中を見てみる

```bash
cat .gitignore
```

> `cat` = ファイルの中身を表示するコマンド。

**期待する出力**（抜粋）
```
.env
.env.*
!.env.example
*.pem
*.key

node_modules/
__pycache__/
.venv/

.DS_Store
Thumbs.db
.vscode/*
```

### 書き方

| 書き方 | 意味 |
|---|---|
| `.env` | `.env` というファイルを無視 |
| `*.log` | `.log` で終わるファイルを全部無視（`*` は「何でも」） |
| `node_modules/` | `node_modules` フォルダ以下を全部無視（`/` はフォルダの意味） |
| `!.env.example` | **例外**：これだけは無視しない（`!` は否定） |
| `# コメント` | `#` で始まる行はコメント。無視される |

### 動作確認してみる

試しに、秘密情報っぽいファイルを作ってみましょう。

```bash
cd ~/git-lec
echo "OPENAI_API_KEY=sk-dummy-not-a-real-key" > .env
```

> `echo "文字列" > ファイル名` は「その文字列を書いたファイルを作る」コマンドです。

```bash
git status
```

**期待する出力**
```
On branch main
nothing to commit, working tree clean
```

**`.env` が一覧に出てきません。** `.gitignore` が効いている証拠です。

念のため、無理やり add しようとしてみます：

```bash
git add .env
```

**期待する出力**
```
The following paths are ignored by one of your .gitignore files:
.env
hint: Use -f if you really want to add them.
```

**Gitが止めてくれます。** これが `.gitignore` の効果です。

練習用ファイルを消しておきましょう：

```bash
rm .env
```

## `.env` の正しい扱い方

APIキーは `.env` というファイルに書いて、**`.gitignore` で除外する**のが定番です。

### やること

**1. `.env` に本物のキーを書く（これはGitHubに上がらない）**

```
OPENAI_API_KEY=sk-proj-xxxxxxxxxxxxxxxxxxxxxx
DATABASE_URL=postgres://user:password@localhost/mydb
```

**2. `.env.example` に「形だけ」を書く（これはGitHubに上げる）**

```
OPENAI_API_KEY=
DATABASE_URL=
```

**3. `.gitignore` に書く**

```
.env
!.env.example
```

### なぜ `.env.example` を作るのか

**チームの他の人が「何を設定すればいいか」を知るためです。**

`.env` は上げられませんが、**キーの名前だけ**は共有しないと、
新しく参加した人は何を設定すればいいか分かりません。
中身が空の `.env.example` があれば、それをコピーして自分のキーを入れるだけで済みます。

## 🚨 上げてしまった時の対処

**やってしまったら、この順番で動いてください。順番が重要です。**

### 手順1：【最優先】キーを無効化する — 5分以内に

**まず、コードを直すより先に、キーそのものを使えなくします。**

| サービス | やること |
|---|---|
| OpenAI | https://platform.openai.com/api-keys → 該当キーを **Revoke** |
| Anthropic | https://console.anthropic.com/settings/keys → 該当キーを **Delete** |
| AWS | IAM → アクセスキー → **無効化 → 削除** |
| その他 | 「(サービス名) API key revoke」で検索 |

**新しいキーを発行して、`.env` に入れ直します。**

### なぜこれが最優先なのか

> **GitHubから消しても、漏れたキーは無効になりません。**
>
> pushされた瞬間にbotがコピーしている前提で動いてください。
> リポジトリを削除しても、**すでにコピーされたキーは有効なまま**です。
>
> **キーを無効化して初めて、被害が止まります。**

**リポジトリを慌てて消すより、キーを無効化する方が100倍重要です。**

### 手順2：ファイルをリポジトリから外す

```bash
git rm --cached .env
```

> `--cached` を付けると、**手元のファイルは残したまま**、Gitの管理からだけ外れます。
> （`--cached` を付けないとファイル自体が消えるので注意）

```bash
echo ".env" >> .gitignore
git add .gitignore
git commit -m "chore: .env を .gitignore に追加"
git push
```

これで、**今後は上がらなくなります。**

### 手順3：履歴からも消す（必要な場合）

手順2では、**過去の履歴には `.env` が残っています。**
GitHub上で過去のコミットを開けば、まだ中身が見えます。

履歴から完全に消すには `git filter-repo` や BFG というツールを使いますが、
**これは初級編の範囲外です。**

そして正直に言うと：

> **履歴の書き換えは、チームに大きな影響を与える操作です。**
> **1人でやろうとせず、必ず先輩・運営メンバーに相談してください。**
>
> そして繰り返しますが、**履歴を消してもキーは無効になりません。**
> **手順1（キーの無効化）さえ済んでいれば、実害は止まっています。**

### 手順4：報告する

チームで開発している場合は、**隠さずに報告してください。**

- 「やってしまいました、キーは無効化済みです」で十分です
- **黙っている方が、はるかに大きな問題になります**
- **誰でも一度はやります。** 責める文化のチームの方が問題です

## 事故を防ぐ習慣

### 習慣1：commit前に必ず `git diff --staged` を見る

**今日のハンズオン（STEP 5-2）でやったことです。**

```bash
git diff --staged
```

**「今から記録される内容」を目で見る。** これだけで、事故の大半は防げます。

### 習慣2：`git add .` を安易に使わない

```bash
git add .          # 今いる場所以下、全部
```

これは便利ですが、**意図しないファイルを巻き込みます。**

```bash
git add members/taro-yamada.md    # ファイルを名指し
```

**名指しの方が安全です。** `git add .` を使うなら、必ず `git status` と `git diff --staged` で確認してから commit してください。

### 習慣3：プロジェクトを始めたら、まず `.gitignore`

**新しくリポジトリを作った時、最初のcommitで `.gitignore` を入れる。**

GitHubでリポジトリを作る時に、`Add .gitignore` から言語を選ぶだけで、
その言語用の定番 `.gitignore` が自動で入ります。**必ず選んでください。**

### 習慣4：キーをコードに直接書かない

```python
# ❌ 絶対にダメ
client = OpenAI(api_key="sk-proj-xxxxxxxxxxxx")

# ✅ こうする
import os
from dotenv import load_dotenv
load_dotenv()
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))
```

**コードにキーを書かなければ、そもそも漏れようがありません。**

## GitHub側の防御機能

GitHubにも、事故を防ぐ仕組みがあります。

### Secret scanning（自動検出）

**GitHubは、pushされた内容にAPIキーらしき文字列がないか自動で検査しています。**

見つかると：
1. **あなたにメールで警告が来ます**
2. サービス提供者（OpenAIなど）にも通知され、**キーが自動で無効化されることがあります**

> 💡 「OpenAIから急にキーが無効化されたメールが来た」という時は、大抵これです。
> **助けてくれているので、素直に従ってください。**

### Push protection

Publicリポジトリでは、**キーを含むpushをGitHubがブロックする**ことがあります。

```
remote: error: GH013: Repository rule violations found
remote: - Push cannot contain secrets
```

**これが出たら、GitHubがあなたを守ってくれています。** 無理やり回避せず、キーを取り除いてください。

## このページのまとめ

- **一度pushした秘密情報は、後から消しても手遅れ。botが数分で収集する**
- **`.gitignore` に `.env` を書く。** これが第一の防御
- **上げてしまったら、最優先で「キーの無効化」。** リポジトリを消すより先
- **commit前に `git diff --staged` を見る習慣**が、最強の予防策
- **コードにキーを直接書かない**
